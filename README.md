# novel-lore-distill

一个用于把长篇小说或长文本整理成**可追溯设定资料库**的 ZCode Skill。

它适合将 TXT、EPUB/PDF 转出的文本、字幕、长篇资料等内容，整理为角色卡、副本卡、鬼/怪物规则卡、势力卡、道具卡、术语表和大事年表；也支持对旧蒸馏库做来源覆盖审计、漏项修复和索引修复。

> 本项目主要面向 ZCode / Agents 风格的本地 Skill 使用场景。

## 主要能力

- 角色身份卡：身份、别名、能力、关系、关键经历、结局和出场章节
- 副本/闹鬼事件/鬼域卡：地点、触发条件、死亡规则、破解方法、幸存者和结局
- 鬼/怪物规则卡：能力、杀人条件、克制方式、阶段演变和最终状态
- 势力、组织、团队卡
- 重要道具卡
- 术语和世界观词典
- 按章节排序的大事年表
- 同名人物、别名和阶段性实体的冲突裁决
- 根目录索引和分类目录索引生成
- SillyTavern World Book / Lorebook / 角色卡 JSON 的后续转换基础
- 旧资料库的来源覆盖率、索引链接和卡片质量审计

## 为什么不是普通的“总结小说”

本 Skill 的目标不是写读后感，也不是只输出一篇剧情简介，而是建立一套可以继续查询、编辑和转换的结构化资料库。

它会把长文本拆成多个章节分块，保留中间提取结果和来源链，再进行跨章节合并。每条重要事实尽量带有：

- 来源文件
- 来源分块
- 原文章节
- 相关实体
- 信息状态（核心、次要、仅提及、待复核或传闻）

没有证据的内容不会被写成确定事实。

## 处理流程

```text
原文 TXT / EPUB / PDF 转文本
              │
              ▼
   盘点编码、章节、文件大小和范围
              │
              ▼
       按章节切成多个分块
              │
              ▼
   并行提取角色/副本/鬼/势力/道具/术语/大事记
              │
              ▼
        一级合并：按章节区间归并
              │
              ▼
       终审输入覆盖率检查（全部来源）
              │
              ▼
   二级终审：按实体去重、合并别名和阶段
              │
              ▼
  同名冲突裁决、卡片分层、索引和别名映射
              │
              ▼
          全量审计与可选 JSON 转换
```

## 输出目录

默认在源文件旁建立一个新的 `<书名>-蒸馏/` 目录，不覆盖原文：

```text
<书名>-蒸馏/
├── 00-总览.md
├── PIPELINE_STATE.md
├── 角色索引.md
├── 副本索引.md
├── 鬼索引.md
├── 势力索引.md
├── 道具索引.md
├── 术语表.md
├── 大事年表.md
├── 别名映射.md
├── 角色/
├── 副本/
├── 鬼/
├── 势力/
├── 道具/
├── 分块文本/
├── 分块提取/
├── 合并/
├── 终审输入/

```

`分块文本/`、`分块提取/`、`合并/`和`修复/`不是无用临时文件，而是审计和断点续跑所需的证据链。

```text

用户级：~/.zcode/skills/novel-lore-distill/
项目级：<project>/.agents/skills/novel-lore-distill/
项目级：<project>/.zcode/skills/novel-lore-distill/
```

```text
D:\Claude\.agents\skills\novel-lore-distill\
```

## 触发方式

自然语言触发示例：

- “把这本小说蒸馏成角色卡和副本卡。”
- “提取这本书所有人物、怪物、势力和道具。”
- “帮我做一套小说世界书。”
- “把这部长篇整理成 SillyTavern Lorebook。”
- “之前的蒸馏库可能漏了几卷，帮我审查和修复。”
- “检查角色卡有没有重复、索引有没有坏链。”

也可以在 ZCode 中显式加载：

```text
/skill novel-lore-distill D:\小说\某部长篇.txt
```

## 使用建议

### 第一次处理一本小说

推荐先试点一卷或前 50–100 章：

1. 检查章节识别是否正确；
2. 确认角色卡和副本卡字段符合需求；
3. 确认“核心/次要/仅提及/待复核”的分层方式；
4. 确认后再运行全书批量任务。

如果用户明确要求直接处理全书，仍然要先说明文本规模、预计分块数和运行成本。

### 全书批量处理

长篇小说通常不能一次放进上下文，应按章节切块。建议每块约 15–25 章，实际大小根据章节长度调整。每个子代理必须读完整自己的分块，不得只读开头或默认 `Read` 一次就代表读完。

并发数不能写死。先用 3–4 个子代理试跑，根据平台返回的并发和配额错误逐步增加；如果出现限制，退回上一次成功的并发数，并只重跑失败编号。

### 需要 SillyTavern 时

先完成 Markdown 资料库、索引和审计，再转换成 World Book/Lorebook 或角色卡 JSON。不要直接把未去重的分块提取结果塞进 JSON，否则容易出现别名重复、规则冲突和章节来源丢失。

## 卡片状态

每类实体都应尽量使用状态字段：

- **核心**：多章节、多来源或主线关键实体
- **次要**：有明确身份和行动，但不是主线核心
- **仅提及**：只有姓名、称呼或一次传闻，资料不足
- **待复核**：来源之间有身份、结局、章节或同名冲突
- **传闻**：只在角色转述中出现，不能当作现场事实

“仅提及”对象不应被静默删除，也不应伪装成完整传记。空白字段可以写“原文未说明”，不要用“输入未提供”制造模板噪声。

## 审计脚本

`scripts/audit_lore_distill.py` 是只读审计工具。它会检查：

- 分块文本和分块提取编号是否连续；
- `merge-01` 至 `merge-09` 是否齐全且七节完整；
- 七份终审输入是否都包含九份主来源；
- 章节范围是否到达首章和末章；
- 卡片是否为空、缺少实体状态或缺少来源；
- 根索引和目录内索引是否存在坏链；
- 仅提及、待复核、短卡、占位字段和规范化重名数量；
- 与修复前基线的数量差异。

运行：

```bash
python scripts/audit_lore_distill.py "D:\小说\某书-蒸馏"
```

带修复前基线：

```bash
python scripts/audit_lore_distill.py \
  "D:\小说\某书-蒸馏" \
  --baseline "D:\小说\某书-蒸馏\修复\repair-baseline.json" \
  --report "D:\小说\某书-蒸馏\修复\audit-report.json"
```

脚本会在 `修复/audit-report.json` 写入机器可读报告；它不会修改卡片和原文。

## 安全与边界

- 不凭记忆补全小说设定；没有原文就停止并索要文本来源。
- 不覆盖原始 TXT、EPUB 或 PDF。
- 覆盖正式卡片目录前先建立备份。
- 不把同名自动当成同一人物；不确定时保留冲突并标记待复核。
- 不擅自纠正原文的章节重号、刊号错位或前后矛盾；保留证据并说明边界。
- 不把候选提取结果冒充已审计定稿。
- 本 Skill 不负责作者思想方法论蒸馏，也不负责人物角色扮演。
